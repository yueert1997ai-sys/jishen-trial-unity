## 验证方法与边界

- 从当前保存的 Assets、Packages、ProjectSettings 创建隔离副本 `unity-audit-20260905`，没有运行 DemoSceneBuilder，没有改写源场景。
- Unity 6000.3.18f1 实际进入 Play Mode，GPU 渲染 1920x1080 画面。没有操作用户鼠标、键盘或桌面。
- UI 通过 EventSystem 的指针点击事件触发；这验证按钮回调，不等于真实鼠标射线遮挡验收。
- 实弹测试使用正常伤害、正常时间流速、自动朝敌人瞄准并调用现有武器。基线站桩、不移动、不无敌；不能用这个测试推断真人操作胜率。
- 另跑旧 DemoPlayModeSmoke。它使用 20 倍时间与直接 Kill 清敌，只证明状态机流程，不证明枪法、手感或自然通关。
- 没有真人连续试玩、物理 WASD/鼠标输入或听感验收。键位绑定有代码证据，不把它当本轮端到端输入测试通过。
- 性能没有完整 Player 帧时间/GC/显存基准；旧 Camera.Render/ReadPixels 压测和批处理帧率不能代替该指标。

## 当前最大五个问题

1. **P0 战斗命中不可靠**：直接损害瞄准与射击最核心体验，不能靠降低难度或换模型解决。
2. **P0 阶段边界不收尾**：强化期间受伤、结果后继续刷怪/攻击/计分的风险；结算缺鼠标入口。
3. **P1 单局成长太薄**：一次选择不是 Survivor-like 成长循环；重玩价值主要靠难度和随机卡片。
4. **P1 可读性/公平性不足**：HUD 强化文本容器不足；Boss 预警方向与发射时朝向可能不同；地图/敌人节奏单一。
5. **P1 验收与文档失真**：通过清敌测试就勾选自然通关、性能、无遮挡；无初始 Git 提交。这会让后续开发反复误判进度。

结论：第一阻碍是基础功能的可靠性，其次是成长与战斗设计深度；表现力确实粗糙，但不是当前最高优先级。

## 代码与性能审计

- GameManager 约 468 行统管状态、UI、统计、难度和旧装备入口，耦合较多但不是必须拆掉的巨型对象。优先补阶段生命周期，不重写总架构。
- 最大文件是 Editor 的 DemoSceneBuilder（约 1200 行），不会产生运行时 Update 负担；但重建会覆盖场景、Prefab、材质，普通启动不能依赖它。
- Find 多数位于初始化，可以接受。导弹无目标时反复全局搜 Damageable，HUD 定时找 Boss，敌人每帧 OverlapSphere 分离，才是随数量增长的风险点。
- 子弹、闪光、碎片和飘字高频 Instantiate/Destroy，无对象池。renderer.material 产生动态材质，缺明确释放；GameAudio 动态 AudioClip 也缺销毁。需 Player Profiler/重复重开内存证据后做局部池化/资源回收，不能宣称已测出泄漏数值。
- Projectile 只靠离散 Trigger，无位移扫掠；同目标多 Collider 可能重复穿透/爆炸伤害。当前单 Collider 敌人降低了触发概率，但扩展前应有回归测试。
- HUD 每帧 new StringBuilder、GetSummary/GetEquippedItems 分配列表/字符串。适合数据变化时刷新或小频率更新，不应为此引入总线框架。
- Damageable 的 OnDamaged/OnDied、武器 BeamFired、玩家 Dashed 已有事件，反馈层有合理解耦；UI 和 GameManager 仍直接绑定。
- 装备使用 SO 合理；波次、武器等级和强化为 switch/硬编码。一旦进入 Build 迭代，再抽取小型升级/波次数据，不为假想内容提前设计庞大系统。
- RefreshEquipment 为空；重新启用旧装备后重算玩家属性可能覆盖局内强化，需要独立接入测试。
