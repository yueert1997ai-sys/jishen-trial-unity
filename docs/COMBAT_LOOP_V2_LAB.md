## 直接体验

继续打开桌面“机神试炼”。默认仍进入完整基础战斗，按 **F9** 进入短战斗。进入时使用当前 M7 或 M14，刀与 SALVO 均可用，固定最远 C 视野。

- **1 / 2 / 3**：换对照方案并重开；默认方案 2。
- **F3**：换 M7 / M14 并重开；**R**：同配置重开。
- **F9**：退出短战斗，回到默认完整战斗；**F8**：退出短战斗并直达 Boss。
- WASD 移动，左键射击，右键 / Q 斩击，空格冲刺，E 导弹，Esc 暂停。

每轮固定 30 秒，死亡会提前结束。清场后约 0.8 秒再次预警生成相同三种敌人；玩家占住预定出生点时，从对侧进入，避免贴脸生成，也避免追杀到出生点后整轮空等。每次重开恢复基础 HP / EN、武器冷却、机体姿态和零强化，清除上轮敌人、子弹、预警、拾取与命中特效。

短战斗不修改永久收藏规则。退出后正常流程继续使用原来的装备获取与存档机制。

## 对照的精确边界

方案 1：完整战斗机制，减少装甲碎片、命中火花、死亡碎件、破防电弧、命中音与震屏。保留实际受击姿态、局部命中停顿、移动、攻击、弹道、前摇预警、血量及状态 UI、开火 / 推进 / 敌方危险提示。它是“基础命中反馈”，不是完全无特效的灰盒。

方案 2：相同机制与参数，使用完整命中反馈。与方案 1 的差别不能改变伤害、冲击、攻击取消、敌人 AI 或 Break 窗口。

方案 3：保留方案 2 的反馈系统，但不积累冲击、不触发 Break、不获得 Break 追击倍率或处决。Elite 的方向装甲、射击恢复与导弹规避仍保留；该组用于检验 Break 的贡献，不是把所有策略机制全部删掉。不存在的 Break 自然不会产生 Break 声光事件。

HUD 不解释方案差别，但固定编号本身不构成严格双盲。真人测试应变换体验顺序，也不要提前展示本段；分别询问战斗乐趣、重量感和命中确认，再对照实际打法。三个条件下真实人类路线会不同，不能要求整局结果相同。

## 当前参数与原文建议的关系

本轮没有把报告的建议区间硬套成数值表。沿用已验证的 M7 18 伤害 / 0.18 秒 / 30.6 冲击，M14 46 / 0.75 秒 / 105 冲击，SALVO 每次 4 发、每发 20 冲击。巨剑在 Break 时 2.4 倍兑现；Elite 阈值 180、窗口 1.35 秒；Boss 阈值 420、窗口 2.2 秒，普通装甲 0.35 倍伤害。

报告的初始 Break 建议为 1.2–1.8 秒；Elite 已在其中。Boss 暂留更长窗口，让当前俯视场地里的接近与三连斩有兑现空间，后续依据实际追击成功率收紧，而不是只为了符合表格缩短。报告中的透视 FOV 参数不适用于这个正交相机。独立镜头比较仍通过正常试场 F5 / F6 / F7 进行，不与反馈实验混在一起。

## 导出与时间含义

桌面启动的每轮记录保存到 `Launcher/UserData/CombatLabRuns/<轮次>/`，包含：

- `events.csv`：游戏消费命令、枪 / 刀 / 冲刺 / SALVO 动作、已配置子弹、实际扣血、失衡、追击、命中反馈调度、音效调度。
- `frames.csv`：真实时钟帧间隔、模拟步长、暂停标记；首帧与暂停边界不进入分位数。
- `summary.json`：武器、方案、种子、结束原因、有效时间、击破、失衡、实际 HP 损失、计数及帧间隔分位数。

子弹生成事件与命中事件用本轮事件编号关联，池复用时清零。伤害总量按实际丢失的 HP 计算，不把过量伤害算入总量。每类表最多 16384 行，超限会明确计数；不会在每一帧写磁盘。切换、重开、死亡、到时、退出或正常关闭游戏时保存。

这里测到的是引擎消费命令与安排反馈的时刻，**不是鼠标物理按下到屏幕发光的时间，也不是扬声器真实起音**。事件间隔使用单调的 wall_s；game_s 是 Unity 的游戏时钟，物理回调会处在固定步进时刻，不能把它直接当作屏幕呈现时刻。固定步长、自动输入、后台运行会写入摘要标记。自动测试里的 P99 不能作为正常玩家帧率或报告所提“10 分钟稳定 60 FPS”的验收结果。录像导出包含渲染和磁盘开销，也不能拿来做性能排名。

## 对照实际发现并修复的问题

逐帧录像暴露了刀击停顿混用时钟的问题：刀刃、缓冲和 Break 按游戏时间前进，局部命中停顿却按真实帧耗时扣减。因此固定模拟速度下，录制开销会改变几帧后才能接下一刀。受控检查中，0.095 秒停顿在 30 Hz 应为 3 个模拟帧，原实现因单帧约 28.8 ms 的真实耗时变成 4 帧。

PlayerMeleeController 的局部停顿现在与战斗共用 Time.deltaTime。验证分别在 30 / 60 / 120 Hz、每帧额外约 25 ms 工作负载下检查 3 / 6 / 12 个模拟帧；基础与完整反馈均执行这项检查。离线音频保存也改为先静音，再退出录制，避免保存文件期间恢复扬声器输出。

另一个失败来自测试假设：整局采用的是会响应敌人位置的同一决策策略，并非逐帧锁步模拟；绝对时钟、物理触发和枪口姿态可能产生一个帧边界的差异，随后策略输入也会分叉。整局击杀与伤害不能硬断言完全相等。最终机械等价由相同目标、相同攻击、相同窗口与受控时钟检查证明，完整三轮结果全部保留用于观察。失败日志和修复前的事件数据没有删除。

## 代码与验证

`CombatLabSettings` 仅保存临时实验开关，默认关闭。`P0CombatDemo` 复用现有敌人生成、暂停、重开、结算和 HUD，管理 30 秒轮次。`CombatLabTelemetry` 记录事件并在轮次结束后解绑监听。ImpactStability 只在方案 3 下跳过状态收益；既有反馈入口只在方案 1 下减少装饰反馈；EquipmentLoop 在短战斗期间禁用装备掉落与吸收。默认完整战斗不会启动记录器。

`CombatLabChecks` 在实际 Player 中检查 A/B 机械等价、C 的状态确实关闭、三敌角色与零成长、暂停、死亡、重开、残留子弹清理、退出恢复、日志完整和存档字节不变；完整三轮使用公开玩家输入，没有无敌、强制伤害、回血或 Buff。单独的状态单元检查使用隔离敌人，不能混作自然战斗证据。
